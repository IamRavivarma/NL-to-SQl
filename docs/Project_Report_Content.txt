1. ABSTRACT
===============================================================================
Large language models (LLMs) such as ChatGPT can answer general questions, but
they do not know the contents of an organisation's private files. They can also
"hallucinate", meaning they give confident answers that are wrong, and they
usually cannot say where an answer came from.

This project is the RAG Data Assistant, a web application. Users upload their
own documents (PDF, Word, text, CSV and Excel) and ask questions about them in
plain English. The system uses Retrieval-Augmented Generation (RAG): each
document is split into small chunks, and each chunk is turned into a vector
embedding using the HuggingFace all-MiniLM-L6-v2 model. The vectors are stored
in MongoDB Atlas Vector Search. For each question, the most relevant chunks
are retrieved and passed to a large language model (openai/gpt-oss-120b on
Groq). The model is instructed to answer only from those chunks and to cite
the file and page.

For spreadsheets the system adds a Natural Language to SQL (NL-to-SQL) module.
Each spreadsheet's rows are loaded into SQL tables, and the LLM converts the
user's question into a read-only SQL SELECT query. The query runs on the
tables, and the answer is built from the exact result rows. This makes totals,
counts, averages and rankings precise. Every answer shows the query used and
its results table, so the user can check how the answer was found.

The backend is FastAPI with a LangGraph agent. The frontend is React with
Tailwind CSS. Answers are streamed word by word, and a dashboard measures
response speed. The system is covered by 135 backend and 31 frontend
automated tests.

Keywords: RAG, LLM, Vector Search, Embeddings, NL-to-SQL, LangGraph, FastAPI,
React, MongoDB Atlas, Groq.


===============================================================================
2. PROJECT OBJECTIVE
===============================================================================
The main objective is a document question-answering system that gives
accurate, verifiable answers from the user's own files. The specific goals
are:

  1. Let users upload PDF, DOCX, TXT, CSV and XLSX files through a simple web
     page.
  2. Extract the text, split it into chunks, and store semantic embeddings so
     that searches match by meaning, not only by keywords.
  3. Answer questions using only the uploaded content, with a citation such
     as [handbook.pdf p.2].
  4. Say "I couldn't find that in your documents." instead of guessing when the
     answer is not in the files (avoiding hallucination).
  5. Convert natural-language questions about spreadsheets into SQL, so that
     numeric answers (sum, count, average, top-N) are exact.
  6. Show the database query and its result rows for every answer, so the
     process is transparent.
  7. Let the user select one uploaded file so it is searched first.
  8. Stream answers in real time and measure performance (time to first word,
     total time, tokens per second).
  9. Keep conversation history so follow-up questions work.

2.1 PROJECT DESCRIPTION & OVERVIEW
-------------------------------------------------------------------------------
The RAG Data Assistant is a "chat with your documents" application. It has
three main parts:

  a) Ingestion (upload)
     - The file is read page by page (PDF/DOCX/TXT) or row by row (CSV/XLSX).
       Each spreadsheet row keeps its column names, for example
       "Name: Priya | Region: North | Revenue: 120000".
     - The text is split into chunks of 1000 characters with a 150-character
       overlap (RecursiveCharacterTextSplitter).
     - Each chunk is converted into a 384-number vector by all-MiniLM-L6-v2,
       which runs locally.
     - The chunks, vectors, file name and page number are saved in the
       MongoDB Atlas "chunks" collection.
     - Spreadsheet rows are also saved as SQL tables in SQLite.
     - Uploads are all-or-nothing: if any step fails, nothing is left behind.

  b) Question answering (LangGraph agent)
     - plan_sql: if spreadsheet tables exist, the LLM is given the table
       schema plus sample rows and asked to write one SQL SELECT, or none.
       The query runs read-only, with a 5-second limit and at most 200 rows.
       If it fails, the LLM gets the error message and one chance to fix the
       query.
     - retrieve: if no SQL answer is possible, Atlas Vector Search finds the
       4 most similar chunks.
     - generate: the LLM writes the answer from the SQL rows or the chunks,
       with citations, and streams it to the browser.

  c) User interface
     - The sidebar has upload (drag and drop), the document list (click a
       file to select it) and the conversation history.
     - The chat area shows the streamed answers, source chips (click to see
       the exact excerpt) and the Query panel (SQL query and results table).
     - The dashboard shows speed charts and usage statistics.

Difference from uploading a PDF to a normal AI chatbot:
  - The files stay in your own database and are reused across chats, with no
    re-uploading.
  - It works with many files at once, even when they are too large for one
    AI prompt.
  - Every answer is cited and shows the query used, so it can be verified.
  - Spreadsheet answers are calculated by SQL, not guessed by the AI.
  - When the information is missing, it says so instead of inventing an
    answer.

4. SYSTEM ARCHITECTURE
===============================================================================
The system uses a three-tier client-server architecture.

  +-----------------------+        HTTP / SSE        +-------------------------+
  |   FRONTEND (React)    | <----------------------> |   BACKEND (FastAPI)     |
  |  - Upload / Doc list  |                          |  - Upload API           |
  |  - Chat + Query panel |                          |  - Query API (stream)   |
  |  - Dashboard          |                          |  - Documents/Stats API  |
  +-----------------------+                          +-----------+-------------+
                                                                 |
          +---------------------------+--------------------------+---------+
          |                           |                          |         |
  +-------v--------+   +--------------v---------+   +-----------v-----+   |
  | Embedding model|   |  MongoDB Atlas         |   | SQLite          |   |
  | all-MiniLM-L6  |   |  - chunks + vectors    |   | spreadsheet     |   |
  | (local, 384-d) |   |  - Vector Search index |   | tables          |   |
  +----------------+   |  - documents, chats    |   +-----------------+   |
                       +------------------------+                         |
                                                          +---------------v--+
                                                          | Groq LLM API     |
                                                          | gpt-oss-120b     |
                                                          +------------------+

4.1 Modules
  1. Ingestion module (app/ingestion)
       loaders.py  - reads PDF, DOCX, TXT, CSV and XLSX into pages and tables
       pipeline.py - chunking, embedding, storing, rollback on failure
  2. RAG module (app/rag)
       embeddings.py   - the HuggingFace MiniLM model
       vector_store.py - Atlas Vector Search and the index definition
       prompts.py      - system prompts (RAG, SQL planner, SQL fix, SQL answer)
       graph.py        - the LangGraph agent: plan_sql -> retrieve -> generate
  3. SQL module (app/sql)
       table_store.py - creates the SQL tables and runs only safe, read-only
                        SELECT queries
       planner.py     - describes the schema to the LLM and parses its SQL
  4. API module (app/api)
       upload, documents, query (streaming), conversations, stats
  5. Data models (app/models) - Document, Conversation, Message (Beanie)
  6. Frontend (frontend/src) - Sidebar, ChatView, MessageBubble, QueryPanel,
       DocumentList, Dashboard

4.2 LangGraph Agent Graph
         START
           |
       [plan_sql] ---- SQL worked ----> [generate] --> END
           |
       no SQL / failed
           |
       [retrieve] ------------------------> [generate] --> END

4.3 Data Storage
  - MongoDB "documents"     : file name, type, size, number of chunks
  - MongoDB "chunks"        : text, embedding (384 floats), file name, page,
                              document_id
  - MongoDB "conversations" / "messages" : chat history, queries, timing
                              metrics
  - SQLite "tables.db"      : one table per CSV file or Excel sheet, plus a
                              catalog table

4.4 Security
  - The SQL connection is read-only (mode=ro, query_only).
  - Only a single SELECT or WITH statement is allowed.
  - Queries are stopped after 5 seconds.
  - API keys are kept in a .env file that is never committed to git.

5. SYSTEM USAGE
===============================================================================
Step 1 - Start the application (see the run commands in the viva guide).
Step 2 - Open http://localhost:5173 in the browser.
Step 3 - Upload a document: drag a PDF, DOCX, TXT, CSV or XLSX file onto the
         upload box, or click it to choose a file (up to 20 MB). The file
         appears in the document list with its number of chunks.
         [Screenshot: upload]
Step 4 - Ask a question in the chat box, for example:
           "How many days of annual leave do employees get?"
           "What is the total revenue in Q2?"
           "Who is the top manager in Q1?"
Step 5 - Read the answer:
           - The Query panel shows the SQL query and its results table.
           - The answer streams in word by word, with citations like
             [handbook.pdf p.2].
           - Click a source chip to see the exact excerpt.
         [Screenshot: chat with query panel]
Step 6 - Optional: click a file in the sidebar to select it. It is
         highlighted, and its name appears in the chat box ("Ask about
         handbook.pdf..."). That file is searched first; click it again or
         the X to go back to all documents.
Step 7 - Ask follow-up questions ("And in Q1?"). The conversation is
         remembered.
Step 8 - Open the Dashboard to see the response time, time to first word,
         tokens per second and usage counts.
         [Screenshot: dashboard]
Step 9 - Delete a document with its trash icon. Its chunks and SQL tables are
         removed too.

7. MODEL EVALUATION
===============================================================================
7.1 Models Used
  - Embedding model: sentence-transformers/all-MiniLM-L6-v2
      * 384-dimensional vectors; cosine similarity
      * Small (about 80 MB) and fast; runs on the CPU
  - Large language model: openai/gpt-oss-120b on Groq LPU
      * Chosen because Groq retired the Llama 3 models named in the brief
      * Very fast token generation; supports streaming
      * temperature 0 for consistent answers

7.2 Evaluation Metrics (measured live for every answer and shown on the
    dashboard)
  - Time to First Token (TTFT): seconds until the first word appears
  - Total response time: seconds until the answer is complete
  - Tokens per second: generation speed
  - Chunks retrieved: the number of passages used (0 for SQL answers)

7.4 Software Testing
  - Backend : 135 automated tests (pytest), all passing. They cover the
    loaders, chunking, SQL safety, the SQL planner, the LangGraph flow, the
    APIs and the vector store.
  - Frontend: 31 automated tests (Vitest), all passing. They cover the query
    panel, chat, document list, API client and message bubbles.
  - Safety tests: DELETE, UPDATE and multiple statements are always
    rejected.

7.5 Why RAG + SQL performs better than the LLM alone
  - The LLM alone cannot see private files, so it guesses.
  - RAG gives it the right passages, so the answers are grounded and cited.
  - The LLM is weak at arithmetic over many rows, so SQL computes exact
    totals.

11. CONCLUSION
===============================================================================
The RAG Data Assistant combines Retrieval-Augmented Generation with Natural
Language to SQL to answer questions from a user's own documents accurately.

Semantic embeddings and MongoDB Atlas Vector Search find the right passages
by meaning, and the LLM on Groq writes fast, streamed answers with citations.
For spreadsheet data, the NL-to-SQL module turns plain-English questions into
safe, read-only SQL queries, so numeric answers are exact rather than
estimated.

Showing the query and its results for every answer makes the system
transparent and trustworthy. Refusing to answer when the information is
missing reduces hallucination. The project meets its objectives and is
backed by 166 passing automated tests. It shows how modern AI tools
(LangChain, LangGraph, vector databases and fast LLM inference) can be
combined into a practical application for colleges, offices and businesses.
